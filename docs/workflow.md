# Workflow

Дисциплина работы с Claude Code: цикл задачи, браузер, контекст, субагенты, антипаттерны.

## Рабочий цикл: Explore → Plan → Implement → Commit

**Explore.** Изучи код, пойми текущее состояние. Glob, Grep, Read. Ничего не меняй.

**Plan.** Переключись в plan mode (`Shift+Tab×2`). Покажи план пользователю. Жди одобрения. Только потом пиши код. Для сложных задач — Annotation Cycle: CC пишет `plan.md` → ты вставляешь заметки `> NOTE: ...` → CC адресует → повтор пока нет вопросов → "Implement the plan".

**Implement.** Код строго по плану. Если план оказался неверным — вернись в Plan, не импровизируй. `Shift+Tab×1` для auto-accept.

**Commit.** Коммит после каждой завершённой подзадачи. Коммит = save point. Английский, осмысленно: `feat: add hero section with stats bar`.

## Claude видит сайт

CC работает не вслепую по коду — встроенный браузер Claude Code Desktop открывает сайт сам:

1. **`preview_start {name: "dev"}`** — поднимает dev-сервер по `.claude/launch.json` (приезжает с шаблоном проекта: `pnpm dev`, порт 3000) и открывает вкладку.
2. **`resize_window`** — обязательная матрица: 375 (mobile), 768 (tablet), 1280 (desktop); при необходимости — light/dark.
3. **`read_console_messages {onlyErrors: true}`** — гейт: ноль ошибок в консоли, прежде чем объявлять «готово».
4. **`javascript_tool`** — объективные проверки вместо «на глаз»: горизонтальный оверфлоу (`document.documentElement.scrollWidth > window.innerWidth`), битые картинки (`[...document.images].filter(i => !i.naturalWidth)`), фактические grid-колонки через `getComputedStyle`.
5. **`computer {action: "screenshot"}`** + `zoom` по региону — визуальная сверка; `read_network_requests` — 404 по ресурсам.

Правила: каждый вызов — с явным `tabId`; браузер — синглтон сессии, им владеет один агент в моменте; первый заход на внешний origin требует одноразового одобрения человеком. Ручной скриншот человеком — fallback: реальное устройство, залогиненные сессии (Chrome-плагин), «не могу воспроизвести».

Формулировки правок — по-прежнему конкретика > абстракция: размеры в px, цвета в hex/класс, отступы в Tailwind-классах.

## Управление контекстом

Точные проценты заполнения — иллюзия: система, MCP-схемы и история съедают долю контекста непредсказуемо, а качество падает задолго до лимита. Честные эвристики:

- **Не тяни сессию за ~60% контекста.** Новая сессия дешевле деградации.
- **Одна сессия = одна задача** (один spec) **или одна оркестраторная волна.** Закончил — новый чат.
- **Document & Clear лучше `/compact`:** `Dump current progress, open decisions, and remaining tasks to handoff.md` → `/clear` → в новом чате `Read handoff.md and continue`. Ты контролируешь, что сохранится.
- `/catchup` после `/clear` восстанавливает контекст по изменённым файлам ветки. Команда и `.claude/settings.json` приезжают вместе с шаблоном проекта.
- Ссылайся на файлы `docs/`, не инлайнь их через `@file` в `CLAUDE.md`. Держи не больше 5–8 MCP-серверов — каждый добавляет схемы в контекст.
- `claude -c` — продолжить последнюю сессию, `claude -r` — вернуться к конкретной.

## Оркестратор и субагенты

Два режима работы (подробности, брифы, гейты — `docs/orchestration.md`):

- **Интерактив** — полноправный дефолт. Человек ведёт одну сессию: правка, багфикс, одна спека.
- **Оркестрация** — крупные пласты: полный сайт, rollout страниц, recreate. Оркестратор читает только `CLAUDE.md`, `specs/INDEX.md`, память и целевую спеку; кода не пишет, браузер не трогает — раздаёт брифы субагентам и принимает структурированные отчёты.

Роли: **builder-sonnet** (быстрые задачи: scaffold, rollout, extend), **builder-opus** (сложные: шаблоны, performance, recreate-секции), **verifier** (независимая приёмка по «Done when»: read-only + браузер, не видит переписку строителя), **integrator** (файлы-перекрёстки: sitemap, layout.tsx, Header/Footer).

Правила:
- В `.claude/memory/` пишет **только** оркестратор (или единственная интерактивная сессия). Субагентам память read-only.
- Doom-loop субагента = перезапуск с новым брифом, не «дожимание». Две неудачи → эскалация человеку.
- Writer/Reviewer-паттерн = builder + verifier: пишет один, судит другой, свежим контекстом.
- Гейты: после субагента — `pnpm typecheck && pnpm lint`; verifier — после крупных пластов; человек — только на своих точках (одобрение заказчика, ключи, DNS).

## Doom Loop и обработка ошибок (интерактив)

**Правило двух попыток.** Если CC не починил с двух попыток — стоп:
1. `/clear` — сброс контекста.
2. Переформулируй проблему с учётом того, что узнал.
3. Дай CC свежий контекст (KB-файлы + описание).

**Признаки, что пора бросить сессию:**
- CC повторяет одни и те же изменения по кругу.
- CC начинает менять код, который уже работал.
- CC предлагает «упростить», удалив функционал.
- CC говорит «pre-existing issue» или «out of scope» — это отмазки.

**Anti-rationalization.** Если CC заявляет, что задача выполнена, а ты видишь, что нет — скажи прямо: «This is not done. [Конкретно что не так]. Fix it.»

## Спецификации (`specs/`)

Каждая крупная задача = один файл в `specs/`, нумерация `00→14`. Шаблон — в `specs/templates/spec-template.md`. Полная последовательность — в `specs/INDEX.md`.

Минимальная структура спеки:
- **KB files to read first** — список `docs/*.md` (CC грузит только их, не всё)
- **Goal** — 1–2 предложения
- **Requirements** — что именно нужно
- **Tasks** — нумерованный список подзадач
- **Boundaries** — что можно/нельзя без подтверждения
- **Done when** — критерии готовности

Запуск спеки:
```
Read and execute specs/04-homepage-and-approval.md.
Before coding:
1. Read the KB files listed in the spec.
2. Show me your implementation plan.
3. Wait for my approval before writing any code.
```

## Верификация

- Давай CC тесты и команды для самопроверки — он работает драматически лучше, когда может проверить результат (`pnpm typecheck && pnpm lint` + браузерные гейты выше).
- Коммить **перед** большими изменениями.
- Один subagent = один deliverable, не план.

## Git-дисциплина

- Работай в ветке `dev`, в `main` попадаем только через PR — см. `docs/deploy.md`.
- Коммит после каждой подзадачи. Сообщения на английском, краткие.
- Не коммить: `.env`, `data/`, `node_modules/`, лог-файлы.
- Перед мержем в main — проверь на localhost.
- **После `gh pr merge` локальный `main` устарел.** Обновляйся только ребейзом на `origin/main` (`git fetch origin && git rebase origin/main`) — мерж локального `main` в рабочую ветку реально терял чужой PR.

## Hooks — гарантии вместо инструкций

Хуки работают на 100%, инструкции в `CLAUDE.md` — на ~70%. Готовый `.claude/settings.json` (защита `main`, блок `rm -rf`, автоформат) приезжает вместе с шаблоном проекта.

## Антипаттерны — что не делать

- **Kitchen sink сессия.** Несколько разнородных задач в одном чате. → Одна задача = один чат.
- **Исправляю×5.** CC ошибся, опять ошибся, контекст отравлен. → После 2 попыток `/clear`.
- **Раздутый CLAUDE.md.** 300+ строк, CC игнорирует половину. → Ориентир ~150 строк; всё справочное — в `docs/`.
- **«Сделай красиво».** Абстрактные запросы = абстрактный результат. → Конкретные размеры, цвета, px.
- **Вайбкодинг без плана.** 20 решений × 80% = 1% шанс, что всё правильно. → Plan mode всегда.
- **Забыл закоммитить.** CC сломал, откатить нельзя. → Коммит после каждой подзадачи.
- **Один чат на весь день.** К вечеру CC деградирует. → Новый чат на каждую задачу.
- **Скриншоты руками там, где CC видит сам.** → Сначала встроенный браузер, ручной скриншот — fallback.
