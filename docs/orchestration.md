# Orchestration — оркестратор и субагенты

Режим для крупных пластов работы: оркестратор планирует волны, субагенты строят параллельно, verifier принимает. Определения агентов — `.claude/agents/*.md`. Вход в режим: **автоматический** при крупной задаче (см. ниже) или явный командой `/orchestrate <цель>`. Краткая выжимка — в `docs/workflow.md` § «Оркестратор и субагенты»; здесь — полные правила.

## Когда оркестрация, а когда интерактив

**Маршрутизация автоматическая, по размеру задачи.** Для крупных пластов оркестрация — **дефолт**: получив такую задачу, Claude сам объявляет вход в режим и действует как `/orchestrate` (план волны + один батч-вопрос) — не дожидаясь команды. Для точечных задач дефолт — интерактив: человек ведёт одну сессию сам. `/orchestrate` — явное принуждение (запустить волну для средней задачи); просьба «сделай в интерактиве» — обратное переопределение. Параллелизм и свежий контекст субагентов окупаются на крупном:

| Задача | Режим |
|---|---|
| Точечная правка, багфикс, одна статья, одна спека | Интерактив |
| Сайт целиком (02 → 12), rollout всех страниц (06) | Оркестрация |
| Recreate донора, полный redesign | Оркестрация |
| 2–4 однотипные страницы | По ситуации; интерактив дешевле |

## Роли и модели

| Роль | Модель | Делает | НЕ делает |
|---|---|---|---|
| **Оркестратор** | Opus | План волн, брифы, приём отчётов, батч-вопросы человеку, память, ledger | НЕ пишет код, НЕ читает `docs/`, НЕ смотрит браузер |
| **builder-sonnet** | Sonnet | Быстрые задачи: scaffold (02), страницы по готовому шаблону (06), блог (07), extend (13) | Архитектурные решения — эскалирует |
| **builder-opus** | Opus | Сложные: шаблоны страниц (05), главная (04), формы (09), performance (11), recreate-секции | То же |
| **verifier** | Opus | Независимая приёмка по «Done when»: read-only + браузер | НЕ чинит; НЕ видит переписку строителя |
| **integrator** | Sonnet | Только конфликтные файлы: merge fan-out, sitemap/nav/layout | Не трогает страницы и секции |

**Оркестратор токен-экономный.** Читает ТОЛЬКО: `CLAUDE.md`, `specs/INDEX.md`, `.claude/memory/INDEX.md` + `project_state.md`, целевую спеку. Не читает `docs/` (единственное исключение — этот файл, прочитанный один раз при входе в режим) — предметное знание живёт у субагентов: они грузят KB по списку «KB files to read first» из брифа. Раскладку «кому делегируется» бери из строки `> Оркестрация:` в шапке каждой целевой спеки.

## Цикл волны

1. **План.** Какие спеки/страницы входят в волну, какие агенты, что параллельно, где verifier (см. матрицу ниже).
2. **Батч-вопрос человеку.** ВСЕ HITL-пункты волны одним списком — ключи, доступы, подтверждения, выбор вариантов. Один вопрос на волну, не десять по ходу.
3. **Брифы.** По одному на субагента, самодостаточные (формат ниже).
4. **Параллельный запуск.** Независимые задачи — одновременно; конфликтные — последовательно (см. «Конфликтные файлы»).
5. **Приём отчётов.** Сверка с «Done when», разбор отклонений и вопросов.
6. **Verifier** на крупный пласт (см. «Гейты»).
7. **Ledger + память.** Обновить `## Task ledger` в `project_state.md`, зафиксировать решения/уроки.
8. **Сводка волны** человеку → следующая волна с шага 1.

## Механика сессии

- **Одна оркестраторная волна = одна сессия** (тот же контекст-бюджет ~60%, что и в интерактиве — см. `docs/workflow.md`). Волна не влезает — режь волну, а не тяни сессию.
- Субагенты определены в `.claude/agents/` (builder-sonnet, builder-opus, verifier, integrator) — Claude Code подхватывает их автоматически; каждый работает в собственном чистом контексте и умирает после отчёта.
- Ветки/worktree субагентов — `claude/*`. После приёма волны оркестратор мержит результат в `dev` и прибирает ветки; осиротевшие ловит `/resume` (предлагает удалить, сам не удаляет).
- Конец сессии — `/handoff`: Session log пишется в формате ledger (см. `.claude/commands/handoff.md`).
- Число параллельных билдеров держи разумным: 2–4. Больше — дороже принимать отчёты, чем строить.

## Формат брифа субагенту

Бриф самодостаточен: субагент не видит историю оркестратора и других агентов.

```
Задача: [что сделать — один абзац]
Спека: specs/NN-name.md (или page-spec)
KB files to read first: docs/a.md, docs/b.md
Память (выжимка ≤5 строк): [только релевантные решения/фидбек/уроки]
Boundaries: [что нельзя трогать: конфликтные файлы, чужие зоны, память]
Done when: [проверяемые критерии — по ним судит verifier]
```

Пример (rollout одной страницы услуги, спека 06):

```
Задача: страница /services/land-survey по page-spec, на базе ServicePageTemplate.
Спека: specs/pages/land-survey.md
KB files to read first: docs/content-layout.md, docs/design-motion.md
Память: заказчик запретил стоковые фото людей (feedback 2026-05-12);
  CTA-формулировка «Получить расчёт», не «Заказать».
Boundaries: sitemap.ts, Header/Footer, docs/pages.md не трогать — списком в отчёт.
Done when: страница рендерится на /services/land-survey; все секции из page-spec;
  typecheck+lint зелёные; тексты из docs/content.md, не выдуманы.
```

Ответ субагента — структурированный отчёт, всегда, даже при провале:

- **Сделано** — по пунктам «Done when»: выполнено / нет
- **Файлы** — точные пути
- **Коммиты** — sha + message
- **Отклонения** — что и почему сделано не по брифу (не молча!)
- **Вопросы** — только блокирующие

Конвенции спек в оркестраторе: «Ask first» из спеки = эскалация оркестратору (не человеку напрямую); plan mode = субагент возвращает план оркестратору на утверждение, не начинает код.

## Правила памяти

- В `.claude/memory/` пишет **ТОЛЬКО оркестратор** (или единственная интерактивная сессия). Субагентам память read-only — нужную выжимку они получают в брифе.
- Task ledger — секция `## Task ledger` в `project_state.md`: задача | агент/модель | статус | верификация | коммиты. Пример строки:

| Задача | Агент/модель | Статус | Верификация | Коммиты |
|---|---|---|---|---|
| 06: /services/land-survey | builder-sonnet | done | verifier pass (волна 2) | a1b2c3d |

- `/handoff` оркестраторной сессии пишет Session log в формате ledger (см. `.claude/commands/handoff.md`).
- Триггеры памяти из `CLAUDE.md` действуют и в оркестрации: отклонение субагента, принятое оркестратором, — это решение → `decisions.md`; провал с уроком → `lessons.md`; «нужно от заказчика» из отчёта → строка в `CLIENT-TODO.md`.

## Гейты

| Гейт | Кто/что | Когда |
|---|---|---|
| `pnpm typecheck && pnpm lint` | SubagentStop-хук (`.claude/hooks/subagent-stop.sh`, см. `docs/automation.md`) | Автоматически после каждого субагента |
| verifier | независимый агент | После крупных пластов: 03, 04, 06, 08+09, 11 |
| Человек | заказчик / разработчик | Только свои точки: одобрение главной (04), ключи и каналы (09/10), DNS, приёмка (12) |

Verifier получает ТОЛЬКО чек-лист «Done when» и артефакты (ветку/коммиты/URL) — без переписки строителя. Его протокол:

- `pnpm build`, `pnpm typecheck`, `pnpm lint` — прогоняет сам, отчётам не верит;
- встроенный браузер: resize-матрица 375/768/1280, `read_console_messages {onlyErrors: true}` — ноль ошибок, оверфлоу и битые картинки через `javascript_tool`, скриншоты проблемных мест;
- вердикт по каждому пункту «Done when»: **pass/fail + доказательство** (вывод команды, скриншот, значение из `javascript_tool`);
- сам не чинит — fail уходит оркестратору, тот решает: новый бриф билдеру или эскалация.

## Сводка волны человеку

По завершении волны оркестратор отдаёт короткую сводку (не простыню):

1. **Сделано** — задачи волны со статусами из ledger.
2. **Verifier** — принято / не принято, список fail с доказательствами.
3. **Вопросы** — что всплыло из отчётов и требует человека (пополнить батч следующей волны).
4. **CLIENT-TODO** — новые пункты для заказчика, если появились.
5. **План следующей волны** — одним абзацем.

## Doom-loop субагента

Субагент дважды не закрыл «Done when» → НЕ дожимать в том же контексте и НЕ `/clear`:

1. **Перезапуск**: новый агент с новым брифом — сузить скоуп, добавить в Boundaries то, что узнали из провала, приложить точную диагностику от verifier.
2. Второй перезапуск тоже провалился → **эскалация человеку** с фактами: что пробовали, где именно падает, гипотезы.

Признаки doom-loop в отчётах — те же, что в `docs/workflow.md`: правки по кругу, ломает работавшее, «упростим, удалив функционал».

## Конфликтные файлы

Файлы-перекрёстки правит ТОЛЬКО integrator. Билдеры возвращают ему списки нужных изменений в отчёте:

- `app/sitemap.ts`, `app/layout.tsx`, `components/layout/Header.tsx` / `Footer.tsx`, `docs/pages.md`, `next.config.ts` (redirects)
- Спеки **08 и 09** обе правят `layout.tsx` → строго последовательно, не параллелить.
- Спека **11 (performance)** — соло: freeze дерева, никаких параллельных агентов, пока идёт оптимизация.

## Браузер — синглтон

Панель встроенного браузера одна на сессию, субагенты делят её:

- Браузером владеет **один агент в моменте** — обычно verifier после волны или единственный билдер с визуальной задачей.
- Каждый вызов `mcp__Claude_Browser__*` — с явным `tabId` (без него бьёт по активной вкладке, которую мог сменить другой агент).
- Параллельным билдерам браузерные проверки не выдавать — визуальную приёмку делает verifier.

## Анти-паттерны оркестрации

- **Оркестратор читает docs/ или код** — раздувает контекст, теряет управляемость. Знание — субагентам через брифы.
- **Вопросы человеку по одному** — вместо батча на волну. Человек нужен редко, но по расписанию.
- **Билдер «заодно» правит sitemap** — конфликт с параллельным билдером. Только integrator.
- **Дожимание провалившегося агента** — третья попытка в отравленном контексте дороже перезапуска.
- **Verifier читает отчёт строителя до проверки** — теряет независимость; сначала проверка, потом сверка.
