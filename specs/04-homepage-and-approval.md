> Оркестрация: builder-opus; параллель: нет (блокирует 05+); verifier: да — независимый прогон Done when + человек-заказчик

## Goal

Собрать главную страницу из секций под бизнес-задачу заказчика, выкатить на dev-окружение (или прямо на prod, если dev-поддомен не настроен), показать заказчику, собрать правки, итерировать до одобрения. Без одобрения главной — НЕ переходить к подстраницам.

## Background

Главная — лицо проекта и точка демо. Одобрение главной = одобрение дизайн-системы, тона, структуры. После него подстраницы делаются по тем же лекалам — заказчик не должен возвращать «не тот стиль» на 12-й странице.

Формы здесь работают «фейково» (CTA открывает заглушку или модалку без отправки) — реальная интеграция в спеке 09.

**Если пройдена `specs/optional/opt-design-to-site.md`** (маршрут A развилки «Источник дизайна») — секции главной уже собраны там по макету. Эта спека тогда сокращается до промежуточного деплоя (Tasks § 4) и одобрения заказчика (Tasks § 5–6); Tasks § 1–3 пропускаются. **Одобрение заказчика обязательно всегда**, каким бы путём ни собиралась главная — макет мог нравиться исполнителю, а не заказчику.

## Before starting

- **Деплой живой:** последний GitHub Actions-run зелёный, `https://{domain}` отвечает 200. Если нет — сначала чини деплой по `docs/troubleshooting.md`, потом главная. Иначе «показать заказчику» упрётся в мёртвый прод в самый неудобный момент.
- `pnpm build` проходит на текущей базе (после спеки 03).

## Requirements

- **Анти-монотонность** (правила из `docs/design-motion.md`): подряд не более 2 секций одного паттерна раскладки; на странице от 3 разных паттернов подачи; «сетка карточек» — не дефолт, а один из вариантов. Паттерн выбирается из контента (7 пунктов → табы или аккордеон, а не грид из 7 карточек; этапы → степпер/timeline). Использовать набор паттернов, зафиксированный в decisions.md в спеке 03.
- **Отсутствующие материалы — паттерн «Placeholder + show-флаги»:** данные (кейсы, отзывы, цифры, лицензии) НЕ выдумывать. Нет материала → блок скрывается флагом (например `SITE.showCases = false` в конфиге сайта), а в `CLIENT-TODO.md` появляется строка «что нужно — зачем — что блокирует». Флаг включается, когда заказчик пришлёт материал.

## Tasks

### 1. Сборка секций

1. Из `docs/content.md` определить какие секции нужны (типичный набор: Hero, Stats, Services/Sub-services, Steps, Benefits, Reviews, FAQ, CTA Final)
2. Для каждой секции:
   - Создать `components/sections/[Name].tsx` (server component если нет state)
   - Использовать тип секции из `docs/content-layout.md` (структура, layout, компоненты) + паттерн подачи из `docs/design-motion.md`
   - Заполнить готовым текстом из `docs/content.md`; нет материала → «Placeholder + show-флаг» (см. Requirements), НЕ выдумывать
   - Соблюсти правила H2 (выгода, не «наши преимущества») из docs/content-layout.md
3. Проверить состав по анти-монотонности (см. Requirements): подряд ≤2 секций одного паттерна раскладки, ≥3 разных паттернов подачи на странице. Если не проходит — сменить паттерн у «средних» секций
4. Собрать секции в `app/page.tsx`:
   ```tsx
   export const metadata: Metadata = { /* из docs/seo.md */ }
   export default function Home() {
     return (
       <>
         <HomeHero />
         <Stats />
         <Services />
         {/* ... */}
       </>
     )
   }
   ```

### 2. Клиентские CTA и заглушка форм консультации

5. Создать `components/forms/ConsultationDialog.tsx` (client) — модалка с полями имя/телефон, кнопка submit показывает `toast.success('Заявка принята (заглушка)')` через Sonner. Реальная отправка в спеке 09.
6. Создать `lib/consultation-context.tsx` — глобальный контекст модалки (open/setOpen)
7. Обернуть `<ConsultationDialogProvider>` вокруг `{children}` в `app/layout.tsx`
8. Создать `components/forms/ConsultationButton.tsx` (client, маленький — только кнопка + хук) и заменить им CTA-заглушку в Header из спеки 03. Header остаётся server component — антипаттерн «вирусный client» см. docs/architecture.md
9. Все CTA-кнопки на главной → `ConsultationButton` / `useConsultationDialog().setOpen(true)`

### 3. Адаптив и визуальная самопроверка (встроенным браузером)

Claude проверяет сам, НЕ просит человека скриншотить (ручной скриншот — fallback):

10. Открыть localhost встроенным браузером (`preview_start` + `navigate`), пройти `resize_window` 375 / 768 / 1280 (+ 1920 при желании) со скриншотом на каждой ширине — раскладка не ломается, бургер работает
11. `read_console_messages {onlyErrors: true}` — консоль чистая
12. Проверить контраст текста (WCAG AA ≥ 4.5:1)
13. `pnpm build` — должен пройти без ошибок

### 4. Промежуточный деплой

14. `git add . && git commit -m 'feat: homepage v1' && git push origin dev`. GitHub Actions (если dev-preview настроен в `01b`) задеплоит на `dev.[domain]`. Если preview не настраивали — мёрджим `dev → main` через PR и смотрим на prod-домене.

### 5. Демо заказчику и сбор правок

15. Отправить заказчику URL + краткий чек-лист, что посмотреть:
    - Бренд (цвета, шрифт)
    - Тон и формулировки
    - Структура (порядок секций, что добавить/убрать)
    - Адаптив (мобилка)
    - Любые правки по контенту
16. Получить правки от заказчика — записать в `.claude/memory/feedback.md` (с **Why:** где известно)
17. Итерация: внести правки → коммит → деплой → новый раунд. Повторять до явного «одобрено»

### 6. Зафиксировать одобрение

18. После одобрения создать тег `git tag homepage-approved` (или коммит `feat: homepage approved by client`)
19. Записать в `.claude/memory/decisions.md`: «Главная одобрена [дата], канал: [скрин / сообщение в мессенджере], дизайн-язык зафиксирован. Все подстраницы — в этой же стилистике». В `CLIENT-TODO.md` (секция «Подтверждения») — строка «одобрение главной — получено [дата]»

## Boundaries

- **Always:** коммитить после каждой завершённой секции (save points), показывать заказчику build+deploy, не «локалхост»
- **Ask first:** перед добавлением секций, не указанных в `docs/content.md` (предложить, но не реализовывать без подтверждения)
- **Never:** переходить к 05-subpages-template до явного одобрения заказчика, добавлять реальную CRM-интеграцию (это 09)

## Done when

- Главная собрана из секций, тексты из docs/content.md, ничего не выдумано
- Анти-монотонность соблюдена: подряд не более 2 секций одного паттерна раскладки, на странице от 3 разных паттернов подачи
- Отсутствующие материалы скрыты show-флагами, по каждому — строка в `CLIENT-TODO.md`
- Самопроверка встроенным браузером пройдена: скрины 375/768/1280, `read_console_messages {onlyErrors: true}` пуст
- `pnpm build` проходит
- Деплой на dev/prod выполнен
- Заказчик дал явное «одобрено»
- Тег `homepage-approved` создан; одобрение зафиксировано в `decisions.md` (дата + канал) и в `CLIENT-TODO.md`
- Правки заказчика записаны в `feedback.md`

## Memory updates

- `feedback.md` — все правки заказчика с **Why:** + **How to apply:**
- `decisions.md` — фиксация одобрения главной (дата + канал) + дизайн-язык зафиксирован
- `pointers.md` — пути к секциям главной (HomeHero, Stats, Services и т.д.) — будут переиспользованы
- `project_state.md` — done, следующая `05-subpages-template`
- `CLIENT-TODO.md` (не память, но артефакт) — недостающие материалы + строка об одобрении
