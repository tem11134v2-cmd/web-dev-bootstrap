# Spec [opt]: Перенос-реконструкция дизайна (визуальная миграция Tilda/WP/конструкторов)

> Оркестрация: builder-opus (extraction — владеет браузером) | builder-sonnet / builder-opus (сборка секций — без браузера, из замороженных артефактов); параллель: extraction стр. N+1 ∥ сборка стр. N (см. R12); verifier: обязателен — независимый, получает браузер ПОСЛЕ сборки, судит по замороженным базлайнам

## Когда применять

Заказчик приносит **действующий сайт** (Tilda, WordPress, Wix, любой конструктор), и нужно перенести его на наш Next-стек, **структурно один-в-один**, но без выгрузки кода и переделки чужой вёрстки. Это маршрут **D** развилки «Источник дизайна» (спека 00).

- **Заменяет** основные `03-design-system` → `06-subpages-rollout` (по паттерну `opt-ecommerce`, который замещает 05–06).
- **Композируется с** `opt-migrate-from-existing.md`: тот тянет контент/медиа/URL и держит SEO-наследие (301), этот строит дизайн. Запускать opt-migrate **первым** (или параллельно Фазе 0–1) — его артефакты (`docs/content.md`, `public/images/migrated/`, карта редиректов) являются входом для этой спеки.
- **Возврат в основной поток:** после реконструкции — `08-seo` → `09-forms` → `10-analytics` → `11-performance` → `12-handoff`.
- **Когда НЕ применять:** дизайн донора слабый/типовой → быстрее собрать с нуля по `00-brief` (или через `opt-design-from-references`). Контентный монстр (блог/каталог 100+ страниц) → сначала тянуть контент через CMS API (WP — REST `/wp-json/wp/v2/`), реконструкцию применять только к шаблонам страниц. Синтез из нескольких источников — это `opt-design-from-references`, не сюда.

## Goal

Воссоздать дизайн действующего сайта-донора на нашем Next-стеке **структурно 1:1**, извлекая токены, контент и ассеты из **живой отрендеренной страницы** (computed styles + DOM + CDN) — **`get_page_text` как позвоночник**, — и собрать **весь сайт за один автономный цикл** с объективной проверкой каждого блока и брейкпоинта. Всё в ОДНОМ встроенном браузере: **вкладка A смотрит на донора, вкладка B — на наш localhost**. Не выгрузка кода, не угадывание.

## Background

Выгрузка кода из конструкторов (Tilda — абсолютное позиционирование на фикс-артборд + генерёные классы; WP — PHP/темы/вывод плагинов) даёт модели **шум**: приходится одновременно reverse-инжинирить намерение, переводить чужую парадигму вёрстки и достраивать невидимые ассеты → дрейф, «не тот сайт, половина дизайна другая, фоток нет». Разворот: смотреть на **отрендеренный результат** и **извлекать данные** (точные значения через `getComputedStyle`, текст verbatim, реальные URL ассетов). **Скриншот — для проверки, не для съёма значений.**

Что подтвердил полевой прогон (rus-campers.com, Tilda — вся главная + мобилка):

- **`get_page_text` снимает весь текст страницы за ОДИН вызов** → браузер НЕ узкое место, вся главная реально собирается за один проход.
- **Извлекать, не угадывать — РАВНОМЕРНО к каждому блоку.** Hero/карточки извлекались честно, а хвостовые блоки собирались «on-brand из токенов на глаз» → промахи по фону/заголовку/раскладке. Фиделити-базлайн по ВСЕМ блокам — обязательный гейт ДО сборки.
- **Объективная верификация** (программная проверка оверфлоу / grid / битых `img` + per-block сверка с базлайном) — решение проблемы «честного verifier» вместо holistic-вкусовщины по скриншоту.
- **Допуск: структурно 1:1 + молчаливая чистка очевидного мусора, без деклараций** — не «pixel-perfect» и не «modernize-редизайн».

v2 спеки переписана под **встроенный браузер Claude Code Desktop** (`mcp__Claude_Browser__*`) — прежняя связка «Chrome-плагин + Playwright-превью» больше не нужна.

## Requirements

### R1. Один встроенный браузер, две вкладки
- **Вкладка A — донор:** `tabs_create` → `navigate {url}`. Первый заход на внешний origin требует **одноразового одобрения человеком** (per-origin approval) — предупредить его заранее, чтобы не ловить паузу посреди цикла.
- **Вкладка B — наш билд:** `preview_start {name: "dev"}` — поднимает dev-сервер по `.claude/launch.json` и открывает вкладку.
- **КАЖДЫЙ браузерный вызов — с явным `tabId`.** Без него вызов бьёт по активной вкладке; при двух вкладках это гарантированная порча данных (извлёк «токены донора» из собственного билда — и не заметил).
- **Chrome-плагин (`mcp__claude-in-chrome__*`) — только если донор требует залогиненной сессии** реального Chrome (закрытый ЛК, контент за оплатой). Для публичных страниц не нужен.
- Один dev-сервер на проект: **два `next dev` дерутся за `.next`** → вести перенос в основной папке проекта, не в worktree.

### R2. Детект платформы (curl, дёшево)
Скачать HTML `curl`-ом, искать сигнатуры: `tildacdn`/`t-rec` (Tilda), `wp-content`/`wp-json` (WP), `wixstatic` (Wix), `bitrix`. Платформенных веток нет, но детект задаёт ожидания (Tilda — абсолют ~1550px → переинтерпретировать в `max-w-[1200px]` поток/grid; WP — пагинация/REST). Записать в `docs/spec.md`.

**Scope (честно):** конкретный рецепт (квирки, optim-URL ассетов, карта-конструктор) валидирован **только на Tilda**. На не-Tilda доноре не предполагай готовый рецепт: извлекай с нуля по тем же принципам, находки — в `decisions.md`.

### R3. Чистый захват (clean capture)
Скрыть cookie-баннеры / попапы / чат-виджеты через `javascript_tool` (`display:none` на позиционированный контейнер) — **НЕ кликать «Принять»** (это согласие от имени пользователя). Баннеры часто без класса `cookie`/`popup` (Tilda — `t657_*`): найти по тексту кнопки → подняться к позиционированному контейнеру → скрыть. Контроль — `computer {action:"screenshot"}` по вкладке A; **повторять до чистого кадра**.

### R4. ⭐ Bulk-извлечение (tabId = донор, серийно)
1. **`get_page_text` ОДИН раз → весь verbatim-текст страницы** (все секции + все повторяющиеся карточки разом). Позвоночник: **DOM-порядок текста = порядок секций** → маппинг по индексу.
2. **Карта секций по геометрии** (id / type / height) + **кластеризация повторов** (R6).
3. **Токены** (computed styles через `javascript_tool`): палитра / шрифты / type-scale / контейнер / радиусы / тени / `:root`-переменные. Возврат сериализуется в JSON — объекты отдавать можно; большие ответы **чанковать ради контекста** (полный дамп по всем блокам раздует сессию), никаких фильтров вывода обходить не нужно.
4. ⭐ **Фиделити-базлайн ПО КАЖДОМУ непохожему блоку** — гейт ДО сборки (и эталон сверки в Фазе 4). Плоская запись на блок: `id :: bg :: главный-заголовок (text/size/weight/color) :: flex-direction | grid-template-columns :: число прямых детей контейнера`. bg+heading ловит «не тот фон/заголовок», layout-поля — «не ту раскладку».
5. **Внутренняя структура сложных блоков** (средний этаж — не пропускать, иначе оболочку извлёк, а нутро угадал): паттерн повторяющейся единицы («иконка + лейбл + значение»), порядок и тип полей формы, число колонок внутренней сетки. Тривиальные блоки (заголовок + абзац + кнопка) — пропустить.
6. ⭐ **Мобильный базлайн донора (новое в v2):** `resize_window {preset:"mobile"}` на вкладке донора → извлечь **фактическую мобильную раскладку** (направления flex, видимость блоков, порядок) → вернуть desktop-пресет. Мобильная версия копии строится ПО НЕМУ, а не «всё в колонку по интуиции».
7. **Ассеты и шрифты:** `read_network_requests` — реальные URL (тело конкретного ответа — по `requestId`), плюс приём чистых base-путей (стрипнуть `?query`). Кросс-доменные `@font-face` недоступны через `cssRules` (CORS) → `read_network_requests` или `curl` CSS напрямую.
8. **hrefs / embeds / поля форм:** соц-иконки + ссылки, якоря навигации (`#models`…), id яндекс-карты (`um=constructor:<id>`), placeholder/name полей.
9. **Заморозить:** токены → `globals.css` (стык с `03-design-system`); verbatim-тексты секций → TS-data-модуль (`content/*.ts`, `models-data.ts`); манифест ассетов; **базлайны (desktop + mobile) → файл** (напр. `docs/recreate-baselines.md`) — по нему судит verifier. Дальше на live никто не ходит: сборка и верификация идут по замороженным артефактам. `docs/content.md` (от opt-migrate) остаётся отдельно для SEO/контента.

### R5. Ассеты — Node-скрипт, не вручную
- Один `scripts/dl-*.mjs`: строит правильный optim-URL (Tilda: `/-/resize/<w>x/-/format/webp/<file>.webp`; для уже-`.webp` источников — без повторного `format`), качает, раскладывает по слаг-папкам, документирует провенанс. **Фото никогда не «рисуем».**
- **Политика веса:** слайдеры-галереи тянуть **N первых (3–4)**, не все ~10/карточку. Крупные PNG (лого/фото) прогнать через `sharp` (1.9MB→33KB).
- Шрифты: **лицензионные (напр. Druk Wide) в прод только при лицензии клиента** — иначе близкий бесплатный аналог + пометка.

### R6. Секции — карта по геометрии + кластеризация повторов
Первый `.t-rec`/`<section>` бывает нулевой высоты/служебный (hero может оказаться секцией №4). Находить секции по видимой высоте и содержимому; собрать **карту секций** (тип, высота, текст-семпл). **Кластеризовать повторяющиеся** (одинаковая высота + type + маркерный текст) — кластер строится **одним компонентом + массивом данных** (R7), не N раз.

### R7. Фундамент-компоненты — строить первыми, переиспользовать
Сначала фундамент (переиспользуется Hero/Showcase/Card/Footer), потом секции: контейнер `max-w-[1200px]`, CTA-пилюля, акцент-заголовок, Socials (реальные иконки + ссылки), примитив слайдера, Header (гамбургер `<lg`), Footer, карточка каталога, FAQ-аккордеон, LeadForm. Повторяющиеся секции → **ОДИН компонент + массив данных**.

### R8. Сборка — без браузера, из замороженных артефактов
- **Непохожие секции → каждая из СВОЕГО извлечения** — оболочка (R4.4) + внутренняя структура (R4.5). **Never: строить из общих токенов «на глаз».**
- Повторяющиеся → один компонент + массив данных.
- **Mobile-first из ИЗВЛЕЧЁННОГО мобильного базлайна (R4.6):** база = фактическая мобильная раскладка донора; `lg:` = десктоп-раскладка (Tilda-абсолют → flow/grid). Кнопки `flex-wrap`; хедер — гамбургер `<lg`.

### R9. ⭐ Верификация (tabId = localhost, объективно)
1. Матрица **штатными пресетами `resize_window`: mobile / tablet / desktop = ровно 375 / 768 / 1280**.
2. `javascript_tool`: **оверфлоу** (`getBoundingClientRect().right > clientWidth`), `gridTemplateColumns`, **битые `img`** (`complete && naturalWidth===0`).
3. **Per-block сверка** bg + heading + layout **против замороженного базлайна** (desktop — R4.4, mobile — R4.6).
4. **`read_console_messages {onlyErrors: true}` — программный гейт «0 ошибок консоли»** (новое в v2).
5. Спот-чек: `computer {action:"screenshot"}` + `zoom` по регионам ключевых секций.
6. **A/B-сравнение с донором** (новое в v2): `tabs_select` донор → `zoom` региона → `tabs_select` копия → `zoom` того же региона — при одинаковом resize обеих вкладок.
7. **Сходимость:** fail → фикс → re-eval, лимит ~4 итерации; не сошлось → флаг «needs review» и дальше (graceful, без вечного цикла).

> **Граница объективной проверки:** eval ловит структуру — оверфлоу, число колонок, направление раскладки, фон, заголовок, отсутствующий ассет. Он НЕ ловит точность отступов/кегля и **сжатую картинку** (`object-fit`: при `naturalWidth>0` п.2 пройдёт, а визуально каша). Это закрывают спот-чек (п.5) и A/B-zoom (п.6) — осознанный остаток субъективного.

### R10. Допуск — структурно 1:1, без лога отклонений
**Строить точно по донору**, НО кривые/несимметричные отступы и явный мусор **НЕ копировать** — снапить к разумному значению на чистых Tailwind-утилитах. Это происходит естественно при сборке → отдельная фаза нормализации и лог отклонений НЕ нужны. Полный «modernize»-редизайн (новый type-scale, переосмысление раскладки) — **НЕ делаем**. Формула: *верность донору + молчаливая чистка очевидного мусора, без деклараций.*

### R11. Каденс — весь сайт за сессию (горло = контекст, не браузер)
Дефолт: **весь сайт за один автономный цикл, если ≤~5–10 страниц** — норма. Делить только бóльшие сайты или единичные гигантские страницы (~15000px). Чанк — по объёму контента; «одна секция = одна сессия» и «батч/сессия» — запрещённые дефолты.

**Откуда список страниц (scope):** (1) есть `docs/pages.md` (от opt-migrate) → берём его; (2) иначе sitemap-first — Tilda `/sitemap.xml`, WP `/wp-sitemap.xml` или `/sitemap_index.xml`; (3) фолбэк — краул внутренних ссылок из nav/footer главной, same-origin, 1 уровень, дедуп. Авто-список шумный → **показать человеку и подтвердить scope** (всё / подмножество / + URL руками) — это «Ask first»-гейт. Итог — в `docs/pages.md`.

**Дельта-режим для страниц 2…N — этим держится «весь сайт за сессию»:** токены и фундамент-компоненты заморожены на стр. 1 → **НЕ переизвлекать и НЕ пересобирать.** Общие секции (Header/Footer/CTA) переиспользуются как есть. На каждой следующей странице — только дельта: `get_page_text` → базлайн + внутренняя структура НОВЫХ секций → сборка нового → верификация.

Не влез в сессию → `/handoff` морозит прогресс (замороженные артефакты + done/remaining в `project_state.md`); `/resume` поднимает в дельта-режиме. На первом многостраничнике следи за контекстом и при риске исчерпания — дели, фиксируя факт в `decisions.md`.

### R12. Субагентный режим (см. `docs/orchestration.md`)
- **Браузер — синглтон:** панель одна на сессию, двум агентам одновременно нельзя; им владеет один агент в моменте.
- **Конвейер — единственная выгодная параллель:** extraction страницы N+1 (агент с браузером) идёт параллельно сборке страницы N (билдеры БЕЗ браузера — читают замороженные артефакты).
- **Независимый verifier** получает браузер ПОСЛЕ сборки; судит по базлайнам из замороженных артефактов; переписку строителей не видит.
- **Worktree-изоляция здесь противопоказана** (один dev-сервер, общий `.next`) — бесколлизионность достигается правилом «один компонент = одна секция».

## Tasks — один автономный цикл (Фазы 0–5)

### Фаза 0 — Setup (один раз, серийно)
1. **Детект платформы** `curl`-ом (R2) → `docs/spec.md`.
2. **Список страниц + scope** (R11): `docs/pages.md` / sitemap / краул → показать человеку, подтвердить → записать в `docs/pages.md`.
3. **Поднять вкладку B:** `preview_start {name:"dev"}` → `preview_logs` — компиляция без ошибок. **Свежесть билда:** временный маркер (уникальная строка на странице) → увидеть его `get_page_text` по вкладке B — подтверждение, что localhost отдаёт именно НАШ свежий билд, а не чужой `:3000`/старый.
4. **Поднять вкладку A:** `tabs_create` → `navigate` на донора. Предупредить человека про одноразовый per-origin approval.
5. **Чистый захват** донора (R3) — повторять до чистого кадра.

### Фаза 1 — Извлечение (tabId = донор, серийно) — R4
1. `get_page_text` ОДИН раз → позвоночник текста (порядок DOM = порядок секций).
2. Карта секций по геометрии + кластеризация повторов (R6).
3. Токены computed-styles (JSON, чанковать большое ради контекста).
4. **Фиделити-базлайн bg + heading + layout по всем непохожим блокам** — гейт до сборки.
5. Внутренняя структура сложных секций.
6. **Мобильный базлайн:** `resize_window mobile` → извлечь раскладку → вернуть desktop.
7. Ассеты и шрифты: `read_network_requests` (+ тело по `requestId`) + чистые base-пути.
8. hrefs / embeds / поля форм.
9. Заморозить: токены → `globals.css`, тексты → TS-data-модуль, манифест ассетов, базлайны → файл.

### Фаза 2 — Ассеты (Node-скрипт) — R5
- `scripts/dl-*.mjs`: optim-URL → скачать → слаг-папки → провенанс; `sharp` для крупных PNG; политика веса (N первых на слайдер).

### Фаза 3 — Сборка (без браузера, из замороженных артефактов) — R7, R8
1. Фундамент-компоненты первыми (R7).
2. Повторяющиеся секции → один компонент + массив данных.
3. Непохожие секции → каждая из СВОЕГО извлечения (bg/heading/layout + нутро).
4. Mobile-first из извлечённого мобильного базлайна (R4.6).

### Фаза 4 — Верификация (tabId = localhost) — R9
- `resize_window` пресетами mobile/tablet/desktop (375/768/1280); `javascript_tool` — оверфлоу / grid / битые img.
- Per-block сверка с базлайном (desktop + mobile).
- `read_console_messages {onlyErrors:true}` — 0 ошибок.
- Спот-чек `screenshot`+`zoom`; A/B-zoom против донора (`tabs_select` туда-обратно).

## Boundaries

- **Always:** извлекать из живого DOM (не из выгрузки кода); `get_page_text` ПЕРВЫМ шагом; **фиделити-базлайн bg+heading+layout (+ внутренняя структура сложных секций + мобильный базлайн) по ВСЕМ блокам ДО сборки**; каждый браузерный вызов — с явным `tabId`; скачивать реальные ассеты; на стр. 2+ — дельта-режим; коммит после каждой завершённой секции/кластера.
- **Always — вести человека по чату** (он в спеку не лезет): спросить URL донора (если не дан); предупредить про per-origin approval перед первым заходом на донора; после discovery показать список страниц и спросить scope; в конце перечислить needs-review-флаги. Не молчать и не ждать угадывания.
- **Ask first:** подтвердить scope страниц перед полным циклом (R11); замена лицензионного шрифта донора в проде; полный «modernize»-редизайн сверх молчаливой чистки мусора (R10); удаление страниц донора; деление сайта на сессии, если он крупнее бюджета R11.
- **Never:**
  - **строить секцию из общих токенов «на глаз» без её собственного extraction (bg/heading/layout)**;
  - воссоздавать фото генерацией вместо скачивания;
  - ставить лицензионный шрифт (Druk и пр.) в прод без лицензии клиента;
  - делать рабочую отправку форм здесь (это `09-forms` — здесь только визуал полей);
  - кликать «Принять» на баннерах донора и подтверждать любые согласия от имени пользователя (баннеры — скрывать через `display:none`, R3);

  - дефолтить «батч/секция за сессию» — гнать весь сайт за цикл (R11).
