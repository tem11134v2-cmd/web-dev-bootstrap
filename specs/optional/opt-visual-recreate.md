# Spec [opt]: Перенос-реконструкция дизайна (визуальная миграция Tilda/WP/конструкторов)

## Когда применять

Заказчик приносит **действующий сайт** (Tilda, WordPress, Wix, любой конструктор), и нужно перенести его на наш Next-стек, **структурно один-в-один**, но без выгрузки кода и переделки чужой вёрстки.

- **Заменяет** основные `03-design-system` → `06-subpages-rollout` (по паттерну `opt-ecommerce`, который замещает 05–06).
- **Композируется с** `opt-migrate-from-existing.md`: тот тянет контент/медиа/URL и держит SEO-наследие (301), этот строит дизайн. Запускать opt-migrate **первым** (или параллельно Фазе 0–1) — его артефакты (`docs/content.md`, `public/images/migrated/`, карта редиректов) являются входом для этой спеки.
- **Возврат в основной поток:** после реконструкции — `08-seo` → `09-forms` → `10-analytics` → `11-performance` → `12-handoff`. Отдельной «спеки дозакрытия» нет — это и есть дозакрытие.
- **Когда НЕ применять:** дизайн донора слабый/типовой → быстрее собрать с нуля по `00-brief`. Контентный монстр (блог/каталог 100+ страниц) → сначала тянуть контент через CMS API (WP — REST `/wp-json/wp/v2/`), реконструкцию применять только к шаблонам страниц.

## Goal

Воссоздать дизайн действующего сайта-донора на нашем Next-стеке **структурно 1:1**, извлекая токены, контент и ассеты из **живой отрендеренной страницы** (computed styles + DOM + CDN) — **`get_page_text` как позвоночник**, — и собрать **весь сайт за один автономный цикл** (zero → вся главная + адаптив), с объективной проверкой каждого блока и брейкпоинта через `Claude_Preview` (`eval`/`inspect`, не «на глаз по скриншоту»). Не выгрузка кода, не угадывание.

## Background

Выгрузка кода из конструкторов (Tilda — абсолютное позиционирование на фикс-артборд + генерёные классы; WP — PHP/темы/вывод плагинов) даёт модели **шум**: приходится одновременно reverse-инжинирить намерение, переводить чужую парадигму вёрстки и достраивать невидимые ассеты → дрейф, «не тот сайт, половина дизайна другая, фоток нет». Вывод: выгрузка кода окупается только при reuse «как есть» на той же архитектуре.

Разворот: смотреть на **отрендеренный результат** и **извлекать данные** (точные значения через `getComputedStyle`, текст verbatim, реальные URL ассетов), а не угадывать. **Скриншот — для проверки, не для съёма значений.**

**Что подтвердил полевой прогон** (rus-campers.com, Tilda — вся главная + мобилка, см. `algorithm-improvements.md`):

- **`get_page_text` снимает весь текст страницы за ОДИН вызов** → браузер НЕ узкое место. Повторяющиеся секции строятся одним компонентом. Поэтому ВСЯ главная реально собирается за один проход — старое «одна секция/страница = одна сессия» избыточно консервативно.
- **Извлекать, не угадывать — РАВНОМЕРНО к каждому блоку.** Hero/карточки извлекались честно, а хвостовые блоки на первом проходе собирались «on-brand из токенов на глаз» → промахи по фону/заголовку/раскладке (см. R10, провал §B-1). Фиделити-базлайн (bg + heading + layout) по ВСЕМ блокам — обязательный гейт ДО сборки.
- **Объективная верификация через `Claude_Preview` `eval`/`inspect`** — это РЕШЕНИЕ проблемы «честного verifier»: программная проверка оверфлоу / grid / битых `img` + per-block сверка с базлайном вместо holistic-вкусовщины по скриншоту. Зафиксировано как принцип (R9).
- **Допуск: структурно 1:1 + молчаливая чистка очевидного мусора, без деклараций** (R10) — не «pixel-perfect» и не «modernize-редизайн».

## Requirements

### R1. Инструментарий — извлечение и верификация разнесены
**Два браузерных инструмента смотрят в РАЗНЫЕ места, не путать:** Chrome-плагин → на **ЖИВОЙ донор** (извлечение); `Claude_Preview` → на **НАШ `localhost`-билд** (верификация).
- **Извлечение из донора — Chrome-плагин** (`mcp__Claude_in_Chrome__*`): `navigate`, **`get_page_text`** (весь текст за 1 вызов — ядро), `javascript_tool` (computed styles), `read_network_requests`, `find`, `computer` (screenshot / scroll / hover / click).
- **Верификация нашей копии — `Claude_Preview` MCP** (Playwright, реальный вьюпорт, ходит на `localhost`): `preview_resize`, `preview_eval`, `preview_inspect`. Штатный объективный верификатор (R9). **`resize_window` Chrome-плагина НЕ годится** — не сужает вьюпорт (`innerWidth` застревает ~2080).
- Браузер — **один серийный ресурс** (extraction сериализуется), но **НЕ узкое место**: `get_page_text` снимает страницу разом. Узкое место — **контекст сессии** (см. R11).
- **Preview-сервер — один, и владеет им `Claude_Preview`** (стартует `next dev` из `launch.json`: абсолютный node, `-p <free>` — см. env-готчи). **Вручную второй `next dev` НЕ поднимать** (дерутся за `.next`). Что localhost отдаёт ИМЕННО наш свежий билд (а не чужой `:3000`/старый) — проверить `curl`+`grep` на входе в верификацию (Фаза 4), не в Setup. **Перенос лучше вести в ОСНОВНОЙ папке** проекта (worktree-`:3000` отдаёт чужой билд).

### R2. Детект платформы (дёшево, информирует квирки)
Скачать HTML, искать сигнатуры: `tildacdn`/`t-rec` (Tilda), `wp-content`/`wp-json` (WP), `wixstatic` (Wix), `bitrix`. Платформенных веток нет, но детект задаёт ожидания (Tilda — абсолют ~1550px → переинтерпретировать в `max-w-[1200px]` поток/grid; WP — пагинация/REST). Записать в `docs/spec.md`.

**Scope v1 (честно):** весь конкретный рецепт ниже (квирки, optim-URL ассетов, карта-конструктор) валидирован **только на Tilda**. WP/Wix/Bitrix — детект есть, платформенные квирки и пайплайн ассетов под них **TODO**. На не-Tilda доноре не предполагай готовый рецепт: извлекай с нуля по тем же принципам и фиксируй находки в журнал `visual-recreate-plan.md`.

### R3. Чистый захват (clean capture)
Скрыть cookie-баннеры / попапы / чат-виджеты через JS `display:none` по позиционированному контейнеру — **НЕ кликать «Принять»** (это согласие от имени юзера + не приватно). Баннеры часто без класса `cookie`/`popup` (на Tilda — `t657_rectangle`/`t657_rectangle`): найти по тексту кнопки-триггера → подняться к позиционированному контейнеру → скрыть. **Self-check: повторять до чистого кадра.**

### R4. ⭐ Bulk-извлечение — `get_page_text` ПЕРВЫМ шагом (в этом вся экономия)
Серийно, НЕМНОГО вызовов:

1. **`get_page_text` ОДИН раз → весь verbatim-текст страницы** (все секции + все повторяющиеся карточки разом). Это позвоночник, заменяет десятки скриншотов. **DOM-порядок текста = порядок секций** → маппинг по индексу.
2. **Карта секций по геометрии** (record id / type / height) + **кластеризация одинаковых** (см. R6): напр. 19 карточек модели = `h≈608`, type 396, содержат «Вместительность» → один кластер.
3. **Токены** (computed styles через `getComputedStyle`): палитра / шрифты / type-scale / контейнер / радиусы / тени / `:root`-переменные. Отдавать **плоской строкой** (`[text] fs/fw/color`), не объектом (иначе `javascript_tool` блокирует, см. Готчи). Кросс-доменные `@font-face` недоступны через `cssRules` (CORS) — `curl`-ить CSS/HTML напрямую.
4. ⭐ **Фиделити-базлайн по КАЖДОМУ непохожему блоку за 1 вызов** — извлечь, чтобы сборка строила ПО НЕМУ, а не угадывала. Это и есть «гейт ДО сборки»: факты на руках до первой строки JSX (он же — эталон сверки в Фазе 4). Для списка record-id вернуть плоской строкой:
   `id :: bg :: главный-заголовок(text/size/weight/color) :: flex-direction|grid-template-columns :: число прямых детей контейнера`.
   bg+heading ловит «не тот фон/заголовок»; layout-поля ловят «не та раскладка» — оба класса провалов §B-1.
5. **Внутренняя структура сложных блоков** (средний этаж — НЕ пропускать, иначе §B-1 повторится этажом ниже: оболочку извлёк, а нутро угадал). Базлайн (п.4) даёт только оболочку; для НЕтривиальных секций извлечь и устройство детей: из `get_page_text`-порядка + геометрии — паттерн повторяющейся единицы (напр. «иконка + лейбл + значение»), порядок и тип полей формы, число колонок внутренней сетки. Тривиальные блоки (заголовок + абзац + кнопка) — пропустить.
6. **Bulk-ассеты** (query-стрипнутые base-пути): галереи по карточкам, общий набор иконок-удобств, фото секций, **соц-иконки + hrefs**, **id яндекс-карты** (`um=constructor:<id>`), **поля форм** (placeholder/name).
7. **Заморозить:** токены → `globals.css` (стык с `03-design-system`); **verbatim-тексты секций → TS-data-модуль** — это вход компонентов (напр. `content/*.ts`, `models-data.ts`); манифест ассетов. `docs/content.md` (markdown от opt-migrate) остаётся **отдельно** для SEO/контента — сборка из него не рендерит. Дальше на live никто не ходит — сборка/верификация идут по замороженным артефактам.

### R5. Ассеты — Node-скрипт, не вручную
- Один `scripts/dl-*.mjs`: строит правильный optim-URL (Tilda: `/-/resize/<w>x/-/format/webp/<file>.webp`; для уже-`.webp` источников — **без повторного `format`**), качает, раскладывает по слаг-папкам, документирует провенанс. **Фото никогда не «рисуем».**
- **Политика веса:** слайдеры-галереи тянуть **N первых (3–4)**, не все ~10/карточку (иначе 180+ файлов). Крупные PNG (лого/фото) прогнать через `sharp` (1.9MB→33KB).
- **Извлечение ссылок/embeds/форм (визуал):** hrefs соцсетей/внешних ссылок, embeds (яндекс-iframe по `um=`), якоря навигации (`#models`…), поля форм (placeholder/name/вид). **Только визуальная сторона** — рабочая отправка (`submitLead`, multi-sink) это спека `09-forms`, здесь её НЕ делаем (см. Boundaries).
- Шрифты: **лицензионные (напр. Druk Wide) в прод только при лицензии клиента** — иначе близкий бесплатный аналог + пометка.

### R6. Секции — карта по геометрии + кластеризация повторов
Первый `.t-rec`/`<section>` бывает нулевой высоты/служебный (на rus-campers hero был секцией №4, а не №0). Находить секции по видимой высоте и содержимому; собрать **карту секций** (тип, высота, текст-семпл). **Кластеризовать повторяющиеся** (одинаковая высота + type + маркерный текст) — кластер строится **одним компонентом + массивом данных** (R7), не N раз.

### R7. Фундамент-компоненты — строить первыми, переиспользовать
Сначала фундамент (переиспользуется Hero/Showcase/Card/Footer), потом секции:

- **Инвентарь:** контейнер `max-w-[1200px]`, CTA-пилюля r30, акцент-заголовок (напр. Druk), **Socials** (общий — реальные иконки + ссылки), примитив слайдера (fade + стрелки), Header (гамбургер `<lg`), Footer, ModelCard/карточка-каталога, FAQ-аккордеон, LeadForm.
- **Повторяющиеся секции → ОДИН компонент + массив данных** (`models-data.ts`: N карточек; `FEATURE_ICONS` map label→svg).

### R8. Сборка — из извлечённого, mobile-first
- **Непохожие секции → каждая свой компонент, СТРОИТСЯ ИЗ ИЗВЛЕЧЁННОГО** — оболочка bg/heading/layout (R4.4) + внутренняя структура (R4.5), **не «на глаз из общих токенов»** (это провал §B-1).
- **Mobile-first по построению:** база = всё в колонку; `lg:` = десктоп-раскладка донора (Tilda-абсолют → flow/grid). Кнопки `flex-wrap`. Хедер: гамбургер `<lg`.

### R9. ⭐ Верификация через `Claude_Preview` (объективно, НЕ скриншотом)
На каждый брейкпоинт — **375 / 768 / 1280** (десктоп задавать **ЯВНОЙ шириной** 1280×800; пресет `desktop` = нативное окно превью, см. env-готчи):

1. `preview_eval` → **оверфлоу** (`getBoundingClientRect().right > clientWidth`), `gridTemplateColumns`, **битые `img`** (`complete && naturalWidth===0`).
2. На каждый блок: `eval`/`inspect` bg + heading + layout **против базлайна R4.4**.
3. Визуальный спот-чек: **Chrome viewport-скриншот** ключевых секций — **НЕ `preview_screenshot`** (виснет на длинной/слайдерной странице и внешнем iframe, см. Готчи).
4. **Сходимость:** fail → фикс → re-eval, лимит ~4 итерации; не сошлось → флаг «needs review» и дальше (graceful, без вечного цикла).

> **Граница объективной проверки (выставить ожидание честно):** `eval` ловит структуру — оверфлоу, число колонок, направление раскладки, фон, заголовок, отсутствующий ассет. Он НЕ ловит точность отступов/кегля и **сжатую картинку** (`object-fit`: при `naturalWidth>0` проверка п.1 пройдёт, а визуально каша). Эти измерения по R10/F-4 снапаются (не копируются попиксельно) и держатся только на спот-чеке п.3 — осознанный остаток субъективного, не «100% объективно».

### R10. Допуск — структурно 1:1, без лога отклонений
**Строить точно по донору**, НО кривые/несимметричные отступы и явный мусор **НЕ копировать** — снапить к разумному значению на чистых Tailwind-утилитах. Это происходит **естественно** при сборке → **отдельная фаза нормализации и лог отклонений НЕ нужны** (отличие от прежней версии спеки). Полный «modernize»-редизайн (новый type-scale, переосмысление раскладки) — **НЕ делаем**. Формула: *верность донору + молчаливая чистка очевидного мусора, без деклараций.*

### R11. Каденс — весь сайт за сессию (узкое место = контекст, не браузер)
Дефолт: **весь сайт за один автономный цикл, если ≤~5–10 страниц.** Делить только бóльшие сайты или единичные гигантские страницы (~15000px). Чанк — **по объёму контента**, не по «батчу/сессия». «Одна секция = одна сессия» и «батч/сессия» — **запрещённые дефолты** (костыли старого плана, когда думали, что браузер — горло; с `get_page_text` неверно).

**Откуда список страниц (scope) — discovery + подтверждение:** (1) есть `docs/pages.md` (от opt-migrate) → берём его; (2) иначе **sitemap-first** — Tilda `/sitemap.xml`, WP `/wp-sitemap.xml` или `/sitemap_index.xml` (Yoast); (3) фолбэк — **краул внутренних ссылок** из nav/footer главной, same-origin, 1 уровень, дедуп. Авто-список шумный (пагинация / теги / служебные `/thank-you`) → **показать человеку и подтвердить scope: всё / подмножество / + URL руками** (это «Ask first»-гейт). Если страниц больше бюджета — тут же решить дробление. Итог записать в `docs/pages.md`.

**Калибровка (честно):** проверено на **1 полной странице** (rus-campers, главная + мобилка), и там разработчик вмешался 4 раза. ≤5–10 — **оценка** бюджета (ревизия F-2), на этом объёме ещё **не валидировано**. На первом многостраничнике следи за контекстом и при риске исчерпания — дели, фиксируя факт в журнал плана.

**Дельта-режим для страниц 2…N — вот чем держится «весь сайт за сессию»:** токены и фундамент-компоненты **уже заморожены на стр. 1 → НЕ переизвлекать и НЕ пересобирать.** Общие секции (Header/Footer/CTA) переиспользуются как есть. На каждой следующей странице повторяется только **дельта**: `get_page_text` → базлайн + внутр. структура НОВЫХ секций → сборка нового → верификация. Первая страница тяжёлая (строит фундамент), остальные — быстрая сборка из готового (front-loaded).

**Не влез в сессию → `/handoff`** морозит прогресс (замороженные токены/фундамент + done/remaining страницы в `project_state.md`); **`/resume`** в следующей сессии поднимает в дельта-режиме. Замороженные артефакты — и есть то, что делает цикл resumable (сами команды — в `CLAUDE.md`, не дублируем).

### R12. Мультиагент — опционально, frozen-artifact, отложено
Для визуального переноса мультиагент даёт **малую выгоду** (fan-out-агенты не ходят надёжно в браузер: прогон — 2 агента, 42 tool-use, 0 файлов). Если использовать — **только frozen-artifact**: главный цикл извлекает и замораживает (R4.7), агенты пишут компоненты **без браузера**, читая артефакты; verifier — независимый (не самооценка builder'а). Оркестрация — инструмент Workflow. Сначала наладить ОДИН поток.

## Tasks — один автономный цикл (Фазы 0–5)

### Фаза 0 — Setup (один раз, серийно)
1. **Детект платформы** (R2) → `docs/spec.md`.
2. **Список страниц + scope** (R11-discovery): взять `docs/pages.md` (от opt-migrate) / иначе sitemap / иначе краул → **показать человеку, подтвердить scope** (всё / подмножество / + URL руками) → записать итог в `docs/pages.md`.
3. **Подготовить preview-сервер** (R1 + env-готч `launch.json`): один `next dev` ЭТОЙ папки на свободном порту, владеет `Claude_Preview`. Проверка «свежий наш билд» (`curl`+`grep`) — на входе в Фазу 4, не здесь. Перенос лучше вести в ОСНОВНОЙ папке.
4. **Чистый захват** донора (R3) — повторять до чистого кадра.

## Готчи инструментов (универсальные — на любой машине)

- **`javascript_tool` блокирует широкий вывод → `[BLOCKED]`.** Не только «URL с query»: блокирует любые URL (иногда), **base64**, длинный/JSON-образный текст. Надёжно проходит **короткий plain-text, newline/pipe-разделённый**. Приёмы: ассеты — стрипать `?query`; текст — из `get_page_text`; computed-styles — плоской строкой; большие списки — чанковать.
- **`preview_screenshot`/`inspect` ВИСНУТ (30с)** на: авто-слайдере (`setInterval`+transition), **очень высокой странице** (~15000px/156img), **внешнем iframe** (Яндекс-карта ждёт «idle» вечно). Чистка интервалов НЕ спасает. → Верифицировать `eval`'ом; визуал — **Chrome viewport-скриншотом** (он по экрану, не по всей странице).
- **React async render при проверке через `eval`:** клик/`setState` не отражается в ТОМ ЖЕ `eval` (рендер асинхронный) → проверять состояние **следующим** вызовом.
- **Biome vs Tailwind v4:** `biome check` ругается на `@theme`/`@apply` в `globals.css` («Tailwind-specific syntax disabled») — это не код секций, гейт = `pnpm build`. `<img>` для SVG-иконок даёт warning `noImgElement` — осознанно (next/image для SVG требует `dangerouslyAllowSVG`).
- **Tilda-специфика:** артборд ~1550px абсолют → `max-w-[1200px]` flow/grid. Бейджи (`с ндс`/`в наличии`) + **скрытый ribbon** `ХИТ ПРОДАЖ!` (в DOM у всех карточек, визуально скрыт — **не рендерить**). Иконки-удобства — белые SVG (`_FFFFFF`) в красных квадратах. Карта — Яндекс-конструктор по `um=constructor:<id>` (переиспользовать id донора).

## Boundaries
- **Always:** извлекать из живого DOM (не из выгрузки кода); `get_page_text` ПЕРВЫМ шагом; **фиделити-базлайн bg+heading+layout (+ внутр. структуру сложных секций) по ВСЕМ блокам ДО сборки**; скачивать реальные ассеты; верифицировать через `Claude_Preview` `eval`; на стр. 2+ — дельта-режим (переиспользовать замороженное); коммит после каждой завершённой секции/кластера.
- **Always — вести человека по чату** (он в спек не лезет): на каждом ручном гейте Claude сам говорит, что нужно — в начале спросить URL донора (если не дан); после discovery показать список и спросить scope; если preview/`launch.json` не готов — сказать, что сделать (или предложить вести в основной папке); в конце перечислить needs-review-флаги. Не молчать и не ждать угадывания.
- **Ask first:** **подтвердить scope страниц перед полным циклом** (R11-discovery); замена лицензионного шрифта донора в проде; полный «modernize»-редизайн сверх молчаливой чистки мусора (R10); удаление страниц донора; деление сайта на сессии, если он крупнее бюджета R11.
- **Never:**
  - **строить секцию из общих токенов «на глаз» без её собственного extraction (bg/heading/layout)** — провал §B-1;
  - воссоздавать фото генерацией вместо скачивания;
  - ставить лицензионный шрифт (Druk и пр.) в прод без лицензии клиента;
  - делать рабочую отправку форм здесь (это `09-forms` — здесь только визуал полей);
  - подтверждать OAuth/аккаунтные/платёжные согласия в браузере (cookie-баннеры — можно);
  - жертвовать адаптивом ради пиксель-перфекта на десктопе (Tilda-абсолют → поток/grid);
  - дефолтить «батч/секция за сессию» — гнать весь сайт за цикл (R11).

## Appendix: env-готчи (среда-специфичные — на нормальной машине часть не возникает)

> Вынесены из тела, чтобы не засорять ядро (ревизия §F-3). Возникают на конкретной dev-среде (Windows + mise/corepack, worktree, локальный превью-сервер).

- **`launch.json` для `Claude_Preview` на Windows + mise/corepack:** `pnpm`/`node` не на PATH спавнера → `ENOENT`. Рабочее: `runtimeExecutable` = **АБСОЛЮТНЫЙ путь к `node.exe`** (`process.execPath`), `runtimeArgs` = `["node_modules/next/dist/bin/next","dev","-p","<port>","--turbopack"]`. Один `next dev` на папку (два дерутся за `.next`).
- **`preview_resize desktop` = НАТИВНОЕ окно превью** (в прогоне 360px!) → для десктопа задавать **ЯВНО 1280×800**, не пресетом.
- **Worktree-dev-сервер:** сервер на `:3000` принадлежит главной папке и отдаёт старый билд → новые секции «не рендерятся». → Поднять свой `next dev -p <free>` и верифицировать, **или вести перенос в ОСНОВНОЙ папке проекта** (предпочтительно, ревизия §F-6).
- **`next/image` SSRF-блок на приватный IP:** при превью с локального адреса оптимизатор может отклонять источники на приватных IP — на этапе реконструкции грузить ассеты как статику из `public/`.
- **`resize_window` Chrome-плагина не сужает вьюпорт** (`innerWidth` застревает ~2080) — для адаптива использовать `Claude_Preview` (R1).
